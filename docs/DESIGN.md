# 기술 설계

## 개발 배경과 문제 정의

Hermes 에이전트는 모델이 생성한 인자로 파일을 저장하고 MCP 서비스를 호출합니다. 문체나 작업 규칙을 프롬프트에 넣어도 실제 도구 인자가 그 규칙을 따르는지는 실행 시점에 확인해야 합니다. 예를 들어 패치에서 금지 표현이 발견됐을 때, 그 표현을 새로 쓰는 호출과 기존 문서에서 제거하는 호출에는 서로 다른 처리가 필요합니다.

Guiderails는 도구가 실행되기 전에 프로필 정책을 적용합니다. 모델이 같은 사용자 턴에서 위반 호출을 고칠 수 있도록 후속 요청에 교정 근거를 제공하고, 사용자에게는 현재 세션에서 판정의 요점을 알립니다. Hermes가 도구 실행과 대화 기록을 소유합니다.

## Design Goals

- 도구의 부수 효과가 발생하기 전에 검사 가능한 입력에서 정책 위반을 확인합니다.
- 규칙 설명과 대체 지침을 모델에 전달하고, 같은 배치에서 성공한 작업의 결과를 후속 요청에 보존합니다.
- 대화형 실행 경로의 검사 비용을 제한하고 구조 오류와 검사 자원 부족을 구분합니다.
- 호출에 적용한 정책 버전을 추적하고 프로세스가 중단돼도 감사 내보내기와 정책 적용 상태를 복구할 수 있게 합니다.

## Principles

- **실행 경계의 분리:** 실행 전 훅에서 판정하고 모델 요청 미들웨어에서 교정 문맥을 구성합니다. 사용자 알림은 별도 채널에서 전달합니다.
- **관찰 가능한 입력 기준:** 일반 도구는 제출 인자를 검사하고 지원되는 로컬 편집은 재구성한 파일 후보까지 검사합니다.
- **일관성 단위의 명시:** 호출은 한 정책 스냅샷을 참조하고 반복 거절 상태는 프로필 내 세션과 규칙에 귀속합니다.
- **복구 가능한 상태 전이:** 파일과 SQLite에 걸친 변경은 기록 순서와 재시작 시 확인할 근거를 명시합니다.

## Key Decisions

각 표는 기술적 대안의 특성을 비교합니다.

### Runtime Intervention

| 접근 | 특성 |
| --- | --- |
| 프롬프트 지침 | 도구나 호스트를 변경하지 않고 행동을 유도합니다. 준수 여부는 모델에 달려 있습니다. |
| 실행 후 검사 | 원격 응답이나 실제 산출물을 검사할 수 있습니다. 이미 발생한 변경을 되돌리려면 별도 복구가 필요합니다. |
| 실행 전 훅 **(현행)** | Hermes가 실행할 인자를 받아 차단 여부를 결정합니다. 검사 대상은 훅에서 관찰하거나 재구성할 수 있는 입력으로 한정됩니다. |

### Model Continuation

거절된 호출과 성공한 호출이 한 배치에 있으면 교정에 필요한 정보와 이미 완료된 작업의 결과를 함께 전달해야 합니다.

| 접근 | 특성 |
| --- | --- |
| 도구 실패 결과로만 안내 | 호스트가 만든 실패 기록을 그대로 재사용합니다. 거절된 인자와 결과를 유지할 때만 그 응답이 모델 문맥에 남습니다. |
| 배치 전체 제거 | 거절된 인자 노출을 줄이지만, 성공한 호출 결과도 잃어 모델이 작업을 반복할 수 있습니다. |
| 요청 단위 재구성 **(현행)** | 적격 후속 요청에 세션별 교정 안내를 넣습니다. 기본값 `keep: true`는 실패 이력을 보존하며, `keep: false`는 식별 가능한 거절 호출과 결과 쌍만 지원 형식에서 제거합니다. |

Provider 요청 형식별로 호출과 결과를 연결해야 합니다. 이 변경은 모델에 보낼 요청에만 적용되며 Hermes의 대화 기록은 유지됩니다.



### Announcer

사용자 알림에는 판정 요약만 담고, 상세 규칙과 대체 지침은 모델 교정과 감사 경로에 둡니다.

- **Ink 표시:** `InkTranscriptChannel`은 TUI와 호환 API를 확인한 뒤 원래 세션의 로컬 live 스트림에 `notification.show.detail`을 게시합니다. Ink는 `detail`을 대화의 시스템 줄로 표시하고 짧은 상태 제목의 수명을 관리합니다.
- **공개 메시징:** `PostMessageChannel`은 공개 `ctx.post_message`를 한 번 호출합니다. 이 경로는 메시징 플랫폼과 Ink 어댑터가 선택 전에 미지원인 경우를 맡습니다. 
- **격리와 히스토리:** 두 경로는 Hermes의 `plugins.isolation: in_process`에서 동작합니다. `host` 격리에서는 플러그인 프로세스에 live Gateway가 없고 공개 `post_message`가 지원되지 않습니다. Discord 공개 API에는 `non_conversational` 옵션이 없어 알림의 후속 채널 히스토리 유입을 제어할 수 없습니다. Telegram에서 사용자가 알림을 인용해 답장하면 인용 내용이 별도 문맥으로 처리될 수 있습니다.

### Artifact-aware Inspection

패치의 검색 문자열은 제거할 대상을 가리킬 수 있습니다. 반면 새 표현은 사용자가 제출한 파편이 아니라 그 파편과 기존 내용이 결합된 파일에서만 드러날 수 있습니다.

| 접근 | 특성 |
| --- | --- |
| 인자 문자열 검사 | MCP에도 적용할 수 있습니다. 검색 문자열과 대체 문자열을 구분하려면 경로 선택자가 필요하며, 원격 저장 결과의 내용은 알 수 없습니다. |
| 지원되는 로컬 후보 재구성 **(현행)** | 실제 핸들러가 쓸 것으로 예상되는 내용을 검사합니다. 도구별 쓰기·패치 형식이 맞아야 하며, 검사 이후의 파일 변경은 반영하지 못합니다. |
| 변경 전후 매치 비교 | 기존 위반을 남겨 두는 점진적 편집과 새 위반을 구분할 수 있습니다. 이전 내용과 결과를 모두 검사하고 위치를 비교하는 비용이 듭니다. |

현행 호출 경로는 명시적 인자 선택 규칙에 제출 문자열을 넘기고, 파일 후보에는 `RuleEngine.inspect()`를 사용합니다. 규칙 스키마는 `edit_policy: introduced`와 `whole_result`를 받으며, `RuleEngine.inspect_edit()`에는 기존 일치 위치를 비교하는 구현과 단위 시험이 있습니다. 실행 전 게이트는 `inspect_edit()`를 호출하지 않습니다. 따라서 후보에 남은 기존 표현도 감지될 수 있습니다. 대체 문자열만 따로 검사하려면 해당 인자에 선택자를 지정합니다.



### Bounded Parallel Execution

| 접근                       | 특성                                                             |
| ------------------------ | -------------------------------------------------------------- |
| 우선순위 순차 검사               | 선택되는 규칙이 제출 순서로 결정됩니다. 앞선 규칙의 지연을 그대로 부담합니다.                   |
| 전체 규칙 병렬 검사              | 여러 위반을 수집하기 쉽습니다. 완료를 모두 기다리거나 폭넓은 작업 제출을 감당해야 합니다.            |
| 제한된 병렬 창과 조기 종료 **(현행)** | 제한된 슬롯에서 검사하고 현재 검사 대상에서 먼저 완료된 위반을 사용합니다. 우선순위는 제출 순서에 관여합니다. |

한 호출에서 먼저 확보한 위반으로 판정하므로 모든 인자·파일·규칙의 위반을 수집하지 않습니다. 확인한 위반 없이 자원 한도에 도달하면 검사 생략 알림을 시도하고 통과시킵니다. 구조·효과 오류는 별도 차단 조건으로 유지됩니다.



### Policy Consistency

검사 중 규칙이 바뀌면 후보 검사의 기준과 감사에 남은 정책 digest가 달라질 수 있습니다.

| 접근 | 특성 |
| --- | --- |
| 검사 단계마다 최신 정책 조회 | 새 정책을 빠르게 읽지만 한 호출에 여러 버전이 섞일 수 있습니다. |
| 검사 전체에서 정책 잠금 유지 | reload와 검사를 직렬화합니다. 느린 파일 작업도 정책 갱신을 지연시킬 수 있습니다. |
| 호출 시작 시 불변 스냅샷 포착 **(현행)** | 검사와 감사가 같은 digest를 사용하고 긴 검사는 런타임 잠금 밖에서 진행합니다. 갱신 전에 시작한 호출은 이전 정책으로 마무리할 수 있습니다. |



### Bounded Rejection

동일한 위반을 반복해서 생성하면 호출마다 거절하는 방식으로는 세션을 진행할 수 없습니다. 반대로 감지만 기록하면 모델에 교정 기회를 강제할 수 없습니다.

| 접근 | 특성 |
| --- | --- |
| 위반마다 차단 | 규칙 집행을 지속합니다. 모델이 수정에 실패하면 작업이 정체될 수 있습니다. |
| 감지 기록 후 허용 | Observe 모드의 패턴 판정입니다. 규칙의 영향을 관찰할 수 있지만 위반 호출도 실행됩니다. |
| 세션·규칙별 한도 **(Strict 현행)** | 선택된 위반 규칙의 한도 안에서는 차단하고, 소진 후에는 감사 기록과 경고 예약을 거쳐 허용합니다. 다른 규칙의 거절 예산은 공유하지 않습니다. |

한 호출에 여러 위반이 있어도 첫 판정에서 선택된 규칙만 한도 계산에 사용합니다. 그 규칙의 한도가 소진돼도 다른 위반 규칙을 다시 찾아 차단하지 않습니다. SQLite가 감지와 거절 결정을 같은 트랜잭션에서 확정해 동시 런타임 간 한도를 일관되게 계산합니다.

### Durable Audit

집계 상태와 JSONL 파일에 별도로 쓰다가 중단되면 어느 이벤트를 다시 내보내야 하는지 판단해야 합니다.

| 접근 | 특성 |
| --- | --- |
| JSONL 직접 추가 | 도구로 조회하기 쉽습니다. SQLite 집계와 파일 기록 사이의 중단 지점을 별도로 추적해야 합니다. |
| SQLite에만 보관 | 감지와 집계의 트랜잭션 경계가 단순합니다. 파일 기반 감사 도구에는 별도 추출이 필요합니다. |
| SQLite outbox와 JSONL **(현행)** | 감지·집계와 내보낼 이벤트를 함께 기록합니다. JSONL을 동기화한 뒤 SQLite에서 완료를 표시하며, 둘 사이에서 중단되면 기존 레코드를 대조해 중복 추가를 피합니다. |

감지와 판정을 SQLite에 저장한 뒤 JSONL 내보내기를 시도합니다. 내보내기에 실패하면 저장된 판정을 적용하고 미처리 이벤트를 아웃박스에 둡니다. 아웃박스가 가득 차면 기존 이벤트를 저장 순서대로 내보낸 뒤 감지 저장을 재시도합니다. 검사나 SQLite 기록을 완료하지 못하면 Hermes가 호출을 계속 처리합니다.

### Recoverable Policy Activation

사용자가 검토한 초안만 활성화하고, 관리 YAML 교체와 SQLite 변경 기록 사이에서 중단되더라도 다음 시작 시 적용 여부를 판단할 수 있어야 합니다.

| 접근 | 특성 |
| --- | --- |
| YAML 원자적 교체만 사용 | 파일의 부분 기록을 방지합니다. 교체가 SQLite의 정책 이력과 함께 완료됐는지는 별도로 확인해야 합니다. |
| 정책 원본을 SQLite로 통합 | 변경 이력과 적용을 한 트랜잭션에 넣을 수 있습니다. 프로필 YAML을 직접 관리하는 배포 방식이 바뀝니다. |
| 승인 digest와 변경 저널 **(현행)** | 초안 ID와 digest를 검증하고, 준비 기록에 변경 전후 파일 digest를 남긴 뒤 관리 YAML을 원자적으로 교체합니다. 재시작 시 파일과 기록을 대조해 적용 여부를 판단합니다. |
